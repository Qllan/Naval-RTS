# Naval-RTS — подготовка к сетевой архитектуре R0.13–R0.15

## Что реализовано

### R0.13: авторитетный шаг и входные команды
- `nine/net/clock.py`: фиксированный шаг 60 Гц, ограничение догоняющих
  обновлений. Переполнение времени учитывается, не загружает процесс
  неограниченным числом шагов.
- `nine/net/commands.py`: явная схема входа (`PlayerCommand`),
  строгая проверка последовательности, чисел, осей, действий, координат
  прицела. Клиент не вправе передавать здоровье, кредиты, позиции,
  установленное оборудование или состояние NPC.
- `nine/net/host.py`: `ServerSimulation` — один управляемый игрок в
  существующем `World`. Команды принимаются только от владельца,
  номера пакетов должны монотонно расти. Один пакет на такт остаётся
  в ограниченной очереди. Краткие действия из нескольких пакетов
  объединяются, движение берётся из последнего.
- Одиночный графический `Game` **не переподключён** к серверному
  режиму, чтобы не вводить изменения тайминга и сохранений до появления
  реального сетевого протокола.

### R0.14: идентификаторы и сетевые состояния
- `EntityRegistry`: стабильные за время процесса ID кораблей; ID
  Python-объектов не отправляются по сети.
- `SnapshotStream`: JSON-совместимые whitelisted состояния кораблей.
  Не сериализуются инвентарь, кредиты, генератор случайных чисел,
  внутреннее состояние AI или полная игровая модель.
- Фильтр интереса относительно **серверной** позиции игрока,
  ограничение 128 сущностями по умолчанию, изменения + удаления
  объектов и периодические полные снимки (по умолчанию раз в 60 тиков).
- Метка сектора вычисляется как сетка из областей 2000×2000 единиц.
  Это только метка для будущего распределения, **не шардирование**.

### R0.15: общие индексы и проверки нагрузки
- `PositionGrid` в `nine/spatial.py` индексирует положения объектов
  один раз в такт и может быть **разделён между множеством наблюдателей**.
  Условие дальности и порядок выбора ближайших кораблей соответствуют
  исходному линейному перебору, что проверяется регрессионными тестами.
- В `ServerSimulation.snapshot()` используется кеш индекса на такт.
  Не нужно заново сканировать все сущности для каждого снимка.
- `tools/check_network_foundation.py`: синтетическая нагрузка для
  1000 объектов и 100 наблюдателей, сравнение кандидатов пространственного
  индекса с полным перебором; порог проверяется в CI.
- CI проверяет повторяемость headless-команд, отвергаемые поля
  пакетов, последовательности, владельца, идентификаторы и
  периодическую синхронизацию, delta/interest и сериализацию JSON.

### R0.15: изолированный многопилотный каркас сектора

- `nine/net/sector.py`: `SectorSimulation` поддерживает несколько
  управляемых кораблей с **отдельными** авторизованными каналами
  команд, общим фиксированным тиком и разделяемым индексом.
- Стабильный реестр ID общий для всех клиентских потоков,
  поэтому один и тот же корабль имеет одинаковый ID у разных
  наблюдателей. Вход и выход участника принуждает новый полный
  снимок у оставшихся.
- Задаётся лимит числа сущностей и радиус интереса. Проверяется
  детерминированность движения вне зависимости от порядка регистрации.
- **Этот прототип моделирует только движение нескольких кораблей**:
  нет общего полноценного World, выстрелов, урона, экономики, портов,
  команд флота или сетевого транспорта. Это интерфейс для следующего
  этапа, а не завершённая многопользовательская игра.

## Контракт будущего сервера

```text
Аутентифицированное соединение ──> [transport: пока отсутствует]
         │ клиентские команды seq / управление, без прав на состояние
         ▼
   PlayerCommand.parse  ──> ServerSimulation.submit
         ▼
   фиксированный тик World.update
         ▼
   разделяемый PositionGrid ──> interest/visibility-фильтры
         ▼
   SnapshotStream ──> JSON payload ──> [transport: пока отсутствует]
```

Сервер должен назначать владельца от проверенного соединения, а не
верить полю из сообщения. Нельзя позволять клиенту выбирать ID чужого
судна или произвольную точку обзора.

## Что ещё НЕ сделано и почему это важно

Это **не готовый мультиплеер**. Текущий `World` рассчитан на одного
активного `player` и одну `captain`: требуется слой
`SectorWorld` для нескольких людей со своими кораблями,
инвентарём и сохраняемыми аккаунтами.

До запуска реального публичного сервера необходимо:
1. Надёжная аутентификация, HTTPS/WSS либо другое шифрованное
   соединение, управление сессиями, лимит запросов и аудит.
2. Персональная авторизация всех торговых и игровых операций;
   отдельные состояния капитанов, принадлежность кораблей,
   персистентное хранилище и транзакции.
3. Обработка взаимодействий множества управляемых кораблей:
   урон, коллизии, смерть, порт, флоты, AI, порядок команд.
4. Репликация с ACK/sequence, повторными полными снимками,
   восстановлением после потери пакетов, проверкой версии протокола.
5. **Видимость, защита скрытой информации и античит**: текущий
   интерес-фильтр ограничивает расстояние, но **не учитывает**
   радар/маскировку/препятствия. Пока его нельзя считать безопасным
   для соревновательной игры.
6. Создание/удаление/передача объектов между настоящими секторами,
   балансировка серверов, история событий и восстановление мира.
7. Профилирование реального времени тика и FPS на нагрузках
   будущего выделенного сервера.

## Принятые ограничения

- Протокол снимков v1 ещё внутренний и может измениться до сетевого
  релиза. Стабильность ID гарантирована только **в рамках одного
  процесса**; они не сохраняются в `save.json`.
- Неподтверждённые дельты пригодны только для стендовых испытаний:
  надёжная доставка/ACK должны быть добавлены на сетевом этапе.
- Адаптер `ServerSimulation` поддерживает **одного пилота** в полном
  `World`; изолированный `SectorSimulation` — нескольких пилотов,
  **только с движением**, без общего боевого/экономического мира.
  Это не обещание 100 игроков в текущем клиенте.
- Никакого игрового плейтеста, сокетов или публичных подключений на
  этом этапе не было. Скоростные тесты считают число операций поиска,
  **не FPS/сетевую задержку**.

После R0.15 фокус разработки переносится на крупный художественный
редизайн: освещение, материалы, детали корпусов, цвета и компоновку
портового интерфейса. Архитектура остаётся отдельной проверенной
основой для будущей сетевой работы.
